# Data model

PostgreSQL 15+. Two migrations: `0000_init.sql` builds the shape,
`0001_security.sql` adds the guarantees.

---

## Conventions

- **Every tenant table carries `org_id`** and is protected by row-level security.
- **Money is two columns** — an integer of minor units and a currency code. There
  is no `numeric` money column anywhere, and no floats.
- **Quantities are integers** in the SKU's stock unit.
- **`stock_movements` and `audit_log` are append-only**, enforced by triggers.
- Primary keys are UUIDs, so ids can be generated by the client and carry no
  information about volume or sequence.

## Tables

### Tenancy and identity

| Table | Purpose |
|---|---|
| `organisations` | The tenant. Also holds the autonomy policy — level, caps, confidence floor, kill switch. |
| `users` | People. `password_hash` is scrypt, formatted `scrypt$N$r$p$salt$hash`. |
| `sessions` | Keyed by the **SHA-256 of the token**. The raw token exists only in the cookie. |
| `api_keys` | Same: only a digest is stored, plus a non-secret `prefix` for identification. |

### Catalogue

| Table | Purpose |
|---|---|
| `sites` | Physical locations. |
| `suppliers` | Lead time, minimum order quantity, case multiple, ordering cost. |
| `skus` | Products. Unit cost and price in minor units, perishability, shelf life. |
| `sku_sites` | **Per-SKU, per-site planning state.** ABC/XYZ class, overrides, cached position. |

`sku_sites` exists because the same product can be an A item at a flagship store
and a C item at a depot, and should be managed differently at each. Putting
segmentation on the SKU would force one policy across the whole network.

### The ledger

| Table | Purpose |
|---|---|
| `stock_movements` | **The single source of truth.** Append-only. |
| `stock_snapshots` | Balance checkpoints. A read optimisation, always reconstructible. |
| `lots` | Batches with expiry dates, for FEFO and expiry risk. |
| `daily_demand` | Dense per-day demand, maintained on write. |

`daily_demand` is denormalised on purpose. The forecaster needs a **zero-filled**
series, and deriving one from movements at read time is both slow and easy to get
wrong — a sparse series silently removes the days on which nothing sold, which
makes intermittent demand look continuous and causes the system to order far too
much of a slow mover.

### The agent

| Table | Purpose |
|---|---|
| `agent_runs` | One row per sweep. Counts and value committed. |
| `forecasts` | Method, pattern, rate, residual σ, MASE, confidence, fitted parameters. |
| `decisions` | What it decided, why, and what the gate allowed. |
| `purchase_orders` / `purchase_order_lines` | Orders raised. `placed_at` → `received_at` is what yields observed lead times. |

### Cross-cutting

| Table | Purpose |
|---|---|
| `audit_log` | Append-only record of system actions — logins, approvals, policy changes. |
| `idempotency_keys` | Replay protection. Expires; not a record. |

`audit_log` is separate from `stock_movements` because they answer different
questions: one records what happened to *stock*, the other what happened to the
*system*.

## Event sourcing in practice

```sql
-- What is on hand? Replay from the newest snapshot.
WITH snapshot AS (
  SELECT on_hand, as_of FROM stock_snapshots
  WHERE sku_id = $1 AND site_id = $2
  ORDER BY as_of DESC LIMIT 1
)
SELECT
  COALESCE((SELECT on_hand FROM snapshot), 0) +
  COALESCE(SUM(
    CASE
      WHEN kind = 'ADJUSTMENT' THEN quantity
      WHEN kind IN ('RECEIPT','RETURN','TRANSFER_IN') THEN quantity
      ELSE -quantity
    END
  ), 0) AS on_hand
FROM stock_movements
WHERE sku_id = $1 AND site_id = $2
  AND occurred_at > COALESCE((SELECT as_of FROM snapshot), '-infinity');
```

Point-in-time reconstruction — "what did we think we had on 3 March?" — is the
same query with an upper bound on `occurred_at`. This is what makes stock
valuation defensible at a year end that has already passed.

### Corrections

There is no `UPDATE`. A miscounted receipt is corrected by appending:

```sql
INSERT INTO stock_movements (org_id, sku_id, site_id, kind, quantity, actor, reason)
VALUES ($1, $2, $3, 'ADJUSTMENT', -40, 'user:...', 'Receipt 4812 overcounted by 40');
```

Both the error and its correction remain visible. That is the entire point.

## Tenant isolation

Row-level security, driven by a transaction-local setting:

```sql
CREATE POLICY users_tenant_isolation ON users
  USING (org_id = stockpilot_current_org())
  WITH CHECK (org_id = stockpilot_current_org());
```

The application sets it once per transaction:

```sql
SELECT set_config('stockpilot.org_id', $1, true);
```

The third argument scopes the setting to the transaction, so a pooled connection
handed to the next request cannot carry the previous tenant's identity.

**`FORCE ROW LEVEL SECURITY` is applied to every table.** Without it, the role
owning the schema bypasses every policy — and that is usually the same role the
application connects as, which would make the whole control decorative.

CI applies the migrations to a clean database and fails the build if any table
lacks RLS, so a future migration that forgets it cannot ship quietly.

## Integrity constraints

Encoded in the database as well as the application. The duplication is
deliberate: the application check gives a good error message, the database check
means a bug, a migration script or a `psql` session cannot bypass it.

| Constraint | Rule |
|---|---|
| `movements_quantity_nonzero` | A movement of zero is meaningless |
| `movements_sign_matches_kind` | Only `ADJUSTMENT` may be negative |
| `skus_perishable_has_shelf_life` | A perishable SKU without a shelf life cannot have expiry risk computed |
| `suppliers_order_rules_positive` | `order_multiple ≥ 1`; zero would divide by zero |
| `decisions_confidence_range` | Confidence in [0, 1] |
| `organisations_limits_sane` | Daily cap ≥ per-decision cap; confidence floor in [0, 1] |
| `po_lines_quantities_sane` | Cannot receive more than was ordered |

## Indexes

Beyond the primary and foreign keys:

| Index | Serves |
|---|---|
| `movements_replay_idx` | Position rebuild: `(org_id, sku_id, site_id, occurred_at, id)` |
| `decisions_pending_idx` | The inbox — **partial**, `WHERE state = 'proposed'` |
| `lots_expiring_idx` | Expiry sweeps — partial, `WHERE expires_on IS NOT NULL` |
| `movements_idempotency_idx` | Unique on `(org_id, idempotency_key)` |
| `decisions_fingerprint_idx` | Unique on `(org_id, fingerprint)` — the idempotency of the agent itself |

The partial indexes matter: the decision inbox is a handful of rows out of
millions, and indexing only the proposed ones keeps it small enough to stay
cached.

## Growth and retention

`stock_movements` is the table that grows without bound — roughly
(SKUs × sites × movements per day) rows.

| Rows | Approach |
|---|---|
| < 10M | Nothing. Postgres is comfortable. |
| 10M–100M | Weekly snapshots; archive movements older than two years to cold storage. |
| > 100M | Partition by `occurred_at` range, monthly. |

Snapshot frequency is the main tuning lever: more snapshots mean shorter replays
and more storage. Weekly is a reasonable default for most catalogues.

Two things expire rather than accumulate — `stockpilot_purge_expired()` deletes
spent idempotency keys and sessions, and should run hourly (see
[OPERATIONS.md](OPERATIONS.md)).

**Never delete from `stock_movements` or `audit_log` to save space.** Archive
them. The triggers will refuse the delete anyway, which is the intended
behaviour: recovering space is not a good enough reason to destroy an audit
trail.
